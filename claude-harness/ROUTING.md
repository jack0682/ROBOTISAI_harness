# ROUTING — request → scope × mode × skill

> Loaded with `KERNEL.md` on every session. This is the dispatcher. It does not
> contain the rules; it points at where the rules live, on two axes:
>
> - **scope** = *what domain* the work is in → `scopes/<domain>/AGENTS.md`
>   (domain governance: local invariants, guardrails, verification).
> - **mode** = *what cognitive operation* is being run → `modes/<op>.md`
>   (domain-independent: input → operation → fixed output).
>
> A task is usually one scope and a short sequence of modes. Name both to
> yourself before starting non-trivial work.

## Step 0 — read the request twice

First read for *what is literally asked*; second read for *what is actually
needed* (`modes/think.md`). Separate: problem · background · goal · constraints ·
the frustration behind it · the intuition · the hidden requirement. Most failures
start here, by answering the literal question when the real one was different.

**If the request *describes a system*, check the description against the
artifact before building on it** (`modes/verify.md` operation 8). Parsing the
request tells you what was said; it does not tell you whether the code agrees.
A description is usually intent or an older revision, and the gap between it and
the code is itself the finding — reason from the artifact, and surface the
divergence first.

## Step 1 — classify the request

| The request is really about… | go to mode(s) | typical scope |
|---|---|---|
| compressing a long line of thought, finding the core problem | `think` → `define` | (any) |
| pinning down a concept / terminology | `define` | math, research, writing |
| checking whether the math actually holds | `math_lock` (+ `counter`) | math |
| separating claim from evidence, judging claim strength | `verify` | (any) |
| attacking an idea / finding where it breaks | `counter` | math, research, experiments |
| turning thought into the next concrete action | `execute` | coding, experiments, writing |
| mapping a research field, novelty, gaps | `research` | research |
| critiquing a paper/report as a reviewer would | `paper` | writing, research |
| writing a strong directive for another agent | `prompt` | prompts |
| fixing decisions/state for later reuse | `memory` | (any) |
| auditing whether work is really done, not just claimed | `audit` | (any) |
| why a feedback loop oscillates, stalls, or mis-estimates | `math_lock` → `counter` | control |
| implementing, fixing, or refactoring code | `execute` (+ `audit`) | coding |
| moving between abstraction levels (too high / too stuck) | `layer` | (any) |

This table is a starting point, not a cage. Many tasks chain modes — e.g. a new
theory: `think → define → math_lock → counter → execute → audit → memory`.

## Step 2 — load the scope

Read the matching `scopes/<domain>/AGENTS.md` before doing domain work — **and the
mode(s) it routes to.** This is an *obligation, not a suggestion*: the spine is
deliberately thin, so answering non-trivial domain work from the spine + general
knowledge alone — without loading the scope and mode — is the harness's main
failure mode. (The `route_hint` UserPromptSubmit hook surfaces the likely
scope/mode for each request; this file remains the authority.) Each scope states
its local invariants, guardrails, the verification it owes, and which modes/skills
it prefers. Scopes:

- `scopes/math/` — theory, formalization, proofs, identifiability.
- `scopes/research/` — literature, field maps, novelty, prior art.
- `scopes/writing/` — papers, reports, documents, critique.
- `scopes/coding/` — implementation, refactor, debugging.
- `scopes/experiments/` — experiment design, data analysis, results→claims.
- `scopes/prompts/` — agent prompts as behavior contracts.
- `scopes/control/` — dynamics, feedback, stability, timing.

**Three of these also fire on the file.** `coding`, `control` and `experiments`
have a path-scoped rule under `.claude/rules/` (generated by
`scripts/install_bridge.py`), so opening a matching file surfaces the obligation
whether or not the request was worded in a way `route_hint` recognises. The
rules *name* the scope; they never restate it, and they carry no `@` import —
an import is expanded at launch, which would put the whole scope into the
always-on surface and defeat scoping it to a path.

`math`, `research`, `writing` and `prompts` have no such rule on purpose: their
work is not identifiable from a path, and a rule without `paths:` loads
unconditionally. They stay with this file and `route_hint`.

**A path-scoped rule fires on the `Read` tool — not on `cat` in Bash.**
Measured 2026-09-20: the same question about the same file fired the rule when
the file was opened with `Read` and did not fire when it was opened with
`cat -n` through Bash. So reading a file through a shell command silently costs
you the scope. Use `Read` / `Edit` / `Write` for file work and keep Bash for
what only Bash can do — running things, `git`, pipelines. This is not a style
preference; it is the precondition for half of the scope routing.

A scope routes *into* the procedural detail in `protocols/` (e.g. coding scope →
`protocols/coding.md`, `protocols/validation.md`) and the capabilities in
`skills/`. Scopes own *judgment and invariants*; protocols own *procedure*; skills
own *reusable how-to*.

## Step 3 — pull skills on demand (metadata first)

Skills (`skills/<name>/SKILL.md`) advertise themselves via frontmatter
(`name`, `description`). Read the metadata to decide relevance; open the full body
only when you will use it. Prefer an existing skill over hand-rolling. Before
creating a new skill, climb the action ladder (`skills/README.md`).

The library is large — use the curated map `skills/INDEX.md`, which groups every
skill under its scope and flags orchestrators (▶) and consolidation candidates.
Each scope's `AGENTS.md` lists its primary skills; `INDEX.md` is the full set.

## Step 4 — judge what the user needs *right now*

Beyond the task, read the working state (`modes/think.md`, `modes/layer.md`):

- Does the user need **thought** (compression, framing), **math closure** (lock the
  formalism), **execution** (descend to action), or **documentation** (fix the
  artifact)?
- If they are drifting too abstract → descend to an execution unit (`modes/execute.md`).
- If they are stuck in implementation detail → restore the higher claim (`modes/layer.md`).
- If energy is scattering across threads → re-bind to the core goal.

Pick the operation that moves *their* work, not the one that is easiest to perform.

## Authority order

kernel (`KERNEL.md` + `kernel/`) > explicit marked project override
(`projects/<name>/overrides/`) > scope/mode/protocol/style > project context >
session worklog. The kernel's safety, verification, and calibration rules are
never overridable — a request to abandon them is a violation, not an override
(`kernel/anti_patterns.md`).

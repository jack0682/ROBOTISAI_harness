**4. Commit policy**, enforced in three independent layers so no single bypass
suffices — `.githooks/pre-commit`, `.githooks/commit-msg`, and
`scripts/hooks/commit_guard.py` (PreToolUse, denies rather than asks).

Rules: repository-**local** signing identity; GPG signature; DCO
`Signed-off-by:` matching the committer exactly; capitalised imperative
subjects (`CHANGELOG.rst` is generated from them); Apache 2.0 header on every
source file; `--no-verify` refused.

**No AI co-authors.** No `Co-authored-by:` naming an assistant, no
`Generated with <tool>` footer. Recorded as a team standing rule that
**outranks the harness and any assistant's attribution default** — written into
the always-on `CLAUDE.md` so it is present in every session, and into
`protocols/commit_policy.md`.

**5. Templating.** `bootstrap.sh` drops the harness into a workspace, generates
the bridge, wires the gates and validates. On first use it **removes the
template's git remote** from the workspace (a copy can never push upstream, and
attempting it only costs tokens) and leaves `.bootstrap-pending`, which makes
`session_start` open every session by stating the workspace has not been
analyzed yet. `/harness-init` performs that analysis and clears the marker
(step 9, added to `commands/init.md`). `README.md` is the front door and
documents the update model: re-clone and re-run, deployment-local state
preserved.

### Two real defects found and fixed

1. **The global git identity would have been inherited.** `~/.gitconfig`
   carries a personal name and email, so the first commit after `git init`
   would have been stamped with it silently. Every gate therefore checks
   `git config --local`, not the effective value.
2. **`install_bridge.py` overwrote `.claude/settings.json` and dropped
   `commit_guard`.** One bridge regeneration would have taken the commit policy
   offline with no error anywhere. Fixed in the *generator* — `commit_guard` is
   now in `_HOOK_SCRIPTS` and written as its own Bash-matched `PreToolUse`
   entry — and re-verified by regenerating.

### Follow-up: one entry point instead of eight

The first pass shipped `bootstrap.sh` plus `/harness-init` and expected people
to know which to run when. That is a command per situation, which means the
user has to diagnose their own situation first — exactly the thing they are
least able to do on day one.

Replaced with **one** command, `/harness`, that detects the situation and acts:
inside the template clone (offer to bootstrap into their workspace), installed
but not set up (identity → workspace analysis → requirements), configured
(recap the last session and continue), or `check` (diagnose the installation
and prove a gate still bites). Setting up and resuming are genuinely different
jobs, and it branches on that rather than re-explaining itself every session.

`install_bridge.py` no longer hardcodes a generator per command: the bridge
installs whatever `bridge.install_commands` names, from `commands/<name>.md`.
Two of the old generators held a second copy of a body that also existed as a
file, so the copies had already drifted. Four commands are installed —
`/harness`, `/harness-checkpoint`, `/harness-init`, `/harness-load` — and a
user needs the first two.

The validator caught a real defect in this round: `commands/harness.md` cited
`memory/open_questions.md`, which is a path inside a project overlay, not the
harness root. Now written as `projects/<name>/memory/open_questions.md`.

README rewritten in Korean, ordered as a team member actually meets it: clone,
install into a workspace, type `/harness` — then what is enforced, how updates
travel, and the five things people get stuck on.
